# Compile and publish `@fractality/web` from TypeScript

The client-rendered-Frame work is written in TypeScript and `@fractality/web` converts wholly, which forces that package to gain its first build step — and the reason is mandatory rather than stylistic. It publishes raw `src/*.js` today, but **Node refuses to strip types for any file under `node_modules`** (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`, reproduced on Node 24.12.0), deliberately and not as a bug, so shipping `.ts` the way we ship `.js` is impossible; the failure would appear only for consumers and never in this repo, which is the same class of defect as the `link:` and phantom-dependency bugs found in the 2026-08-14 audit. The compiler is `tsc` alone rather than a bundler: it emits declarations natively, keeps per-file output so stack traces point at files a reader can open, and adds no tool beyond TypeScript itself. `main` and `exports` move to `dist/` with `types` listed first, since export conditions resolve in order; the move is invisible to consumers because that same audit added `exports` maps to every package and closed off deep imports into internals. Source maps ship with `inlineSources` so the maps are self-contained and an error still points at readable source — true today because `src/` is published, and otherwise silently lost. The type boundary deliberately stops at the payload contract: `@fractality/core` and the adapters stay JavaScript and `allowJs` is off, keeping the `mixwith` class-factory layer — the highest-risk part of any TypeScript conversion here — out of scope, at the accepted cost that the derivation from core's models into the payload is guarded by review rather than by tooling until the wider conversion happens.
