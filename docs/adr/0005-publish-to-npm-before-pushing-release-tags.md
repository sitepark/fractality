# Publish to npm before pushing release tags

The release workflow ran `lerna version` and `lerna publish from-git` as two independent steps, so the version commit, the changelogs and the tags were pushed to `main` before npm had accepted a single package. When publishing failed — an expired `NPM_TOKEN`, which npm reports as an opaque `E404 Not found` on the upload rather than an auth error — git had already moved on, and because `from-git` only ever considers the tags on `HEAD`, the skipped versions could never be published by re-running the workflow. Two releases (`0.5.4` and `0.5.5`) were lost that way before the divergence was noticed, and repairing it meant rewriting already-pushed history. Rather than accept that and reach for a different release tool, we reordered the pipeline so npm is the step that can fail cheaply: `lerna version --no-push` keeps the bump, the changelogs and the tags local; `lerna publish from-package` compares each `package.json` version against the registry and uploads only what is missing; and `git push --follow-tags` runs afterwards, so a failed publish leaves the remote untouched and a re-run is an ordinary clean retry. Two further guards fall out of the same idea — the workflow calls `npm whoami` before anything is bumped, so a dead token fails the run in seconds with an actionable message, and `from-package` being idempotent means a release that dies halfway through is completed, not duplicated, by running it again. The trade-off is that `--create-release github` can no longer be used, since it requires the push it is now sequenced after, so GitHub releases are created in a separate step by `scripts/create-github-releases.mjs`, which reads each new tag's notes out of that package's own `CHANGELOG.md`.
