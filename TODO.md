## Maintenance

- [x] **Theming did nothing on `next-major`** (fixed 2026-08-19). `FrctlConfig.theming` was declared in `packages/web/src/shell/config.ts` and populated by neither the dev server nor the builder, and the Shell writer emitted no `:root` block — so `skin: { accent, complement, links }`, the replacement the 0.x → 1.0 guide points every user of a named skin at, was accepted, stored and dropped. It fails silently by construction: `assets/scss` declares `--background-color: rgb(var(--skin-accent))` and then `background-color: var(--background-color, $default)`, so an undefined `--skin-*` is invalid at computed-value time and the Sass default paints instead — nothing 404s, nothing throws, the Frame just never changes colour. Fixed by resolving `skin` to `--skin-*` channel triplets in mandelbrot's `theme.js`, passing `theming` through, and writing a `:root` block into the Shell after the theme's stylesheets. Two things made it possible and both are now closed: the config was assembled **twice**, once in `Server` and once in `Builder`, so a field could be missing from both copies at once (now one `frctlConfigFor()`); and an unknown or unparsable `skin` key was a no-op (now an error at theme construction — a misspelled `link` for `links` is otherwise indistinguishable from theming that does not work)
- [x] **`_env` was empty in every rendered pattern** (fixed 2026-08-19). `@fractality/web` called `entity.render(null, {}, …)` at both of its render sites — `src/dev/preview-routes.ts` and `src/build/previews.ts` — where 0.x passed `{ request, server, builder }`. Not an adapter bug: all four adapters still do `setEnv('_env', meta.env, context)`, so handlebars, nunjucks, twig and react lost it identically. Two symptoms, and the second is the expensive one: `{{#if _env.server}}` in a user's pattern was always false, and the `path` helper/filter — which branches on `_env.server` and then rewrites against `_env.request.path` — took the _build_ branch in **both** modes with the path defaulting to `/`. So `{{path '/some-path'}}` served `./some-path.html` in the dev server (should be `/some-path`) and wrote `./some-path.html` into every built Preview instead of `../../some-path.html`, which resolves inside `components/preview/` and 404s. Verified against all four example projects. The adapter tests never caught it because they pass `{server: true}` / `{builder: true}` to `render()` themselves, so they exercise the helpers without exercising the thing that supplies the env. Fixed by `src/render-env.ts`, one producer for both modes, with the flags derived from a single argument so `server` and `builder` cannot disagree; `Renderable.render()` now types `env` as `RenderEnv` rather than `unknown`, so an empty object no longer type-checks
- [x] **A missing static directory threw away a finished build, and `static.ignored` was dead** (fixed 2026-08-19). `Builder.build()` copied `theme.static()` with a bare `cp()` as its last step, so an unreadable directory rejected _after_ every Shell, payload and Preview was already on disk — the CLI printed a raw `ENOENT: lstat '…/public'` instead of the build summary. 0.x caught copy failures, logged them and counted them into `errorCount`, which is the behaviour restored here. Two of this repo's own examples (`examples/twig`, `examples/react`) set `web.static.path` to a `public/` directory that does not exist, so `pnpm build` failed outright in both. The same rewrite dropped `web.builder.static.ignored`, which used to filter that copy through anymatch and had silently become a no-op — restored with `anymatch` now declared as a dependency of `@fractality/web` rather than borrowed from the root. Both now live in `src/build/static-assets.ts`, per mount and independently, so one failing mount cannot stop the others
- [x] **The Frame linked to urls that do not exist** (fixed 2026-08-19). Two faults with one symptom — a nav link that navigates fine and then 404s the moment the page is reloaded, bookmarked or shared. (1) Every href the navigation built was extensionless, while a static build writes `<route>.html` and nothing at the bare path; the Frame resolves either spelling, so nothing failed until a reload. `Nav` now runs its hrefs through `resolveRouteUrl()`, the same rule the payload-carried Preview urls already used. (2) Documentation pages were linked as `/docs/<handle>` while the Shell and payload are written at `/docs/<path>`, so every page below the docs root was a dead link — a doc's handle is its file's own name, and two pages in different directories can share one. `TreeNode` now carries `path` for docs (an additive contract change, so no version bump), resolved by the same `docRoutePath()` the routes use. And even at the correct url the dev server could not answer: `payload-routes.ts` registered `${docsRoute}/:file`, a single segment, so a nested payload fell through to the Frame catch-all and the Frame parsed a Shell as JSON. Verified end to end in both modes with a nested fixture, including reading the rendered nav out of the built site in a headless browser
- [x] **The home page was empty** (fixed 2026-08-19). `/` is a documentation route — a project's `docs/index.md` is what 0.x rendered there, and it is the url `fractality start` prints and the one a bare domain resolves to — but the Frame's route matching did not recognise it, so every site's front page was a panel reading "Select a component". The index page was reachable only at `/docs/index`. `isDocRoute()` now covers the site root and `fetchDoc()` maps its three spellings (`/`, `/index.html`, `/docs`) onto the one payload that backs it; the navigation marks the index page current there too. A project with no index page gets a Welcome panel rather than an error, since that is the state every new library starts in — which needed the dev server to answer a missing payload with a **404** instead of falling through to the Shell catch-all (200 + HTML, so the Frame reported a JSON parse error and could not tell a missing page from a broken server). One deliberate omission: 0.x's fallback page also tabulated the component statuses with their descriptions, and `description` is not carried in the data contract, so a table built from the tree would be a legend of colours with nothing to explain them
- [x] **Every site called itself "Component Library", and every tab said "Fractality"** (fixed 2026-08-19). The Frame read the project's name from `frctl.labels.projectTitle`, a key nothing sets — mandelbrot's label defaults do not define it and `@fractality/web` only ever injected the theme's labels — so `project.title` reached the page nowhere, and `document.title` was hardcoded to the name of the tool rather than the library being browsed. `FrctlConfig` now carries `projectTitle`, read off the **library's** configuration rather than the theme's (a theme has no business naming the project, and every theme needs it), which is also why `frctlConfigFor()` now takes the app. The document title is `<page> | <project>`, the shape 0.x's `<title>` had, and the welcome page follows 0.x's chain for a page with no document behind it: the project's name, then the greeting
- [x] **`scripts`, `lang` and `rtl` reached the page nowhere** (fixed 2026-08-19). Three consumer options that survived into the config and stopped there. The Shell writer injected the theme's stylesheets and favicon but never its `scripts`, so a consumer's own script URLs were accepted and dropped (0.x linked them from `partials/foot.nunj`); they are now written at the end of the body as classic scripts, which is the order that ran them _before_ the Frame's module. And a theme builds its Shell once, before it knows whose library it will render — mandelbrot's says `lang="en" dir="ltr"` — so `lang` and `rtl` could not be honoured by the theme and were honoured by nobody; `prepareShell()` now sets both on the root element, which is also the only place they can be set without the page painting left-to-right first and flipping. mandelbrot resolves its `rtl` flag into the `dir` value the writer wants, and the whole UI mirrors: the `[dir="rtl"]` rules and the logical-property mixins throughout `assets/scss` were already there, and the Frame's drag arithmetic already read `document.documentElement.dir`. Verified by building an example with `{ rtl: true, lang: 'ar', scripts: [...] }` and rendering it
- [ ] Stylesheet cachebusting was dropped in the CSR rewrite and is not restored: 0.x appended `?cachebust=<theme version>` to every `<link>` and `<script>` it wrote. Vite content-hashes the Frame bundle, but `css/default.css` and `css/highlight.css` are not hashed, so a theme upgrade can serve a stale stylesheet from the browser cache. Worth fixing in the theme rather than in `@fractality/web` — the package passes a theme's URLs through untouched by design, so appending a query string to them is mandelbrot's call, and hashing the filenames at build time would be better than a query string
